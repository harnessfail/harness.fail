A record of security issues that AI agent harnesses failed to prevent.

harness

1. noun: a deterministic program that wraps a model, constructs and manages its context, and mediates the model's inputs and outputs with the surrounding environment (e.g. the OS, tools, files, network, or user).

Every issue on this page happened on the far side of a harness.

Meaning any and all harnesses. When a harness delegates a decision to a model, that decision is no longer deterministic.

fails

1. verb · third person singular present of fail: to not do what it exists to do, or what it is expected to do.

When the harness fails, restricted files enter model context.

2. noun informal · plural of fail: cases of failing.

This page is a collection of harness fails.

Both readings are intended. Sometimes the harness broke; sometimes it was never there.

Motivation

Agent tools can be great multipliers in the right hands. Today's harnesses, however, often pose a security risk to their users. For two decades, the industry moved toward least privilege: apps were increasingly sandboxed and had to ask permission before accessing our personal data. Developer tools were largely the exception, but their failures were as deterministic as the tools themselves. Agent tools have changed the developer landscape: the same multiplier applies to the risk too.

Permission policies are often inadequate, and fail at the very thing they were designed to do. The resulting issues are usually framed by their outcomes and rarely by their root cause, leaving the underlying problem obscured. A problem without a name or a clear definition is hard to discuss and even harder to fix.

With the agentaccess.txt specification, my goal is to propose how file-access policy could be declared in the filesystem and how a harness should enforce it. The record collects documented cases where harnesses failed, and the matrix scores harnesses against abstract requirements derived from the specification.

We must standardize these expectations, so our tools can earn the trust we already give them.

The record

Updated October 8, 2026 · 74 issues · 7 classes · JSON · DOI 10.5281/zenodo.23199129

Some frameworks assume a bad actor and classify the attack (how it is built, what it wants); others classify the harm (what went wrong in the world). harness.fail classifies the failure: the boundary the harness itself was supposed to hold, but didn't, regardless of intent. That is why two of the seven classes, Scaffolding collapse and Ambient activation, have no direct counterpart in OWASP or MITRE ATLAS. These seven classes begin where the harness makes the decision and move outward, through what the agent reads, the tools it connects and the instructions it trusts, to the workspace it opens and the software it was installed from. The last, Excessive agency, is the quietest: every check passes, and the agent does damage anyway with the reach it was given.

Scaffolding collapse

Term introduced here by Peter Seprus, 2026.

Enforcement bugs in non-malicious tools. The tool declares a boundary (a sandbox, a path restriction, an ignore rule, an approval prompt, an access check) and its own code fails to enforce it, so the boundary it promises is not the boundary it enforces. The test: the issue would not exist if the tool enforced exactly what it documents. How the gap is reached does not matter; an injected instruction, a malicious repository and a curious model all count. Scaffolding is the usual word for the code around a model, and here it is that code that gives way. The harness is the bug.

No direct mapping in OWASP or MITRE ATLAS.

Indirect prompt injection

Term introduced by Greshake et al., 2023, extending prompt injection (Simon Willison, 2022).

“We reveal new attack vectors, using Indirect Prompt Injection, that enable adversaries to remotely (without a direct interface) exploit LLM-integrated applications by strategically injecting prompts into data likely to be retrieved.”

Malicious instructions arrive inside material the agent legitimately processes, such as a README, a GitHub issue, a web page or a tool result, and steer the agent into acting for the attacker: leaking files, secrets or credentials, running attacker code, or handing over control of its machine.

OWASP: Prompt Injection (LLM01:2025), Sensitive Information Disclosure (LLM02:2025), Agent Goal Hijack (ASI01), Tool Misuse and Exploitation (ASI02) · MITRE ATLAS: LLM Prompt Injection: Indirect (AML.T0051.001), Exfiltration via AI Agent Tool Invocation (AML.T0086), LLM Response Rendering (AML.T0077)

The matrix

Updated October 8, 2026 · 13 harnesses · 17 requirements · JSON

The capabilities a harness would need to enforce a file-access policy, as derived from the agentaccess.txt specification and written as abstract requirements, grouped under four questions: can the user state a file-access policy, what do its rules actually gate, which way do its errors fail, and does the mechanism hold? Each harness is scored against them from its own documentation, source code, issue tracker and security advisories. A ? means no authoritative statement was found either way, and an undocumented boundary is itself a finding.

● yes, documented ◐ partial, or documented gaps ○ no ? undocumented — not applicable

The requirements

Each requirement links to the specification section it derives from. The specification is one proposal for satisfying them; the requirements stand on their own.

A. Declarative surface — can the user state the policy?

A1 Path rules
User-authorable file-access rules exist at all: an ignore file, deny globs, private-file patterns. §1
A2 Tree-resident
The rules live in the directory they govern and travel with it — clone the tree, keep the policy. Any directory can carry its own policy file, applied by the path being accessed; a single project-root file, or one chosen by where the session starts, is partial. §4
A3 Per-path
Rules distinguish paths by pattern, not only whole-project switches. §5
A4 Per-agent
Rules can name which tool they bind — "tool X may work here, tool Y may not" — and a tool the rules do not name is denied rather than let through. §6
A5 Shared grammar
The rules format is shared across tools rather than a proprietary dialect. §8

B. Coverage — what do the rules actually gate?

B1 Context gating
Restricted content, and the names of restricted paths, are kept out of model context and not transmitted — reads, listings, indexing, attachments — not merely deprioritized. §3, §7
B2 Shell coverage
The restriction holds when the model reaches for the shell — cat, subprocesses, terminal tools. §7
B3 Write gating
Rules cover create/modify/rename/delete, not only reads — a declarative do-not-touch. §7
B4 Pre-flight
Rules are evaluated before content is touched — at workspace open for ambient agents, before each operation otherwise — and a change takes effect no later than the next operation. §4

C. Fail direction — which way do errors fail?

C1 Deny precedence
A restriction holds against tool-native grants: a session approval, allowlist entry, remembered permission or bypass mode does not lift it. §7
C2 Fail-closed policy errors
A malformed or invalid rule, or a policy file that cannot be read, restricts rather than being dropped. §5
C3 Self-protection
The agent cannot create, modify, or delete the policy that restricts it. §7
C4 Policy as data
The policy is evaluated in deterministic code and never enters model context as natural language — a policy the model can read is a prompt-injection surface. §9

D. Enforcement quality — does the mechanism hold?

D1 Harness enforcement
Restrictions are enforced in deterministic harness code, never entrusted to the model's judgment or a system-prompt request. §9
D2 Canonicalization
Symlinks resolved and paths canonicalized before the policy check — a recurring class of enforcement bug. §5, §9, A.6
D3 Deliberate override
A restriction is lifted only by an explicit user action naming that restriction, for one invocation — never by a remembered setting, a blanket bypass mode, or consent the model parsed out of its own context. §7
D4 Delegation
Restrictions carry to subagents and spawned processes; they attenuate through delegation, never reset. §7

What the matrix shows

Four columns carry the headline. Claude Code 2.1.295

permissions.deny with Read()/Edit() path rules (permissions docs) (A1/A3 ●); rules are Claude Code's own JSON settings and bind no other tool (A4 ○, A5 ○); project settings can be committed with the repo (.claude/settings.json), but Claude Code reads that one file "from the session's primary working directory" (settings), with no per-directory files (A2 ◐). Settings edits, permissions included, reach "the running session without a restart", but managed settings delivered by MDM or the claude.ai console "reach a running session on a schedule rather than on save" (B4 ◐). For context surfaces (Grep, Glob, @-mentions, IDE context) the vendor's own wording is a "best-effort attempt" (B1 ◐). Invalid managed sandbox values fail closed per the changelog (2.1.283), and an unparseable managed settings file stops every session; one the OS denies reading starts the session "without that file's policies" (2.1.285); in other settings files a malformed permission rule is skipped — Claude Code "skips those values and keeps the rest of the file in effect" (settings) (C2 ◐). Scoped rules "don't change which tools Claude sees. Claude Code checks them when Claude attempts a call, leaving the prefix intact", and a bare tool-name deny removes the tool rather than describing it (prompt caching) (C4 ●). CVE-2025-54794 was "prefix matching instead of canonical path comparison", fixed; deny rules now "apply when either the requested path or the file it resolves to matches", yet symlink bypasses of Read deny rules through @-mentions, IDE selections and @-mentioned folder listings were still being fixed in 2.1.289–2.1.290 (D2 ◐). Writes to protected paths, .claude among them, cannot be pre-approved by allow rules, yet in auto mode — "the built-in starting permission mode for interactive terminal and VS Code sessions" — they are "Routed to the classifier", and in bypassPermissions they are "Allowed" (C3 ◐). That is also the D3 gap: user deny rules lift only when the user edits them, but the built-in protection falls to a blanket mode, to a classifier model's judgment, and to a prompt option that allows .claude edits "for this session" (D3 ◐). Subagents: built-in ones inherit "the parent conversation's permission rules", a settings deny rule "applies to the main conversation and to subagents", and a subagent that declares bypassPermissions "keeps the main conversation's mode instead"; spawned shell processes carry the rules only inside the opt-in sandbox (D4 ◐).

Cline 4.1.23

.clineignore, gitignore syntax, one file "in your project root" — multi-root workspaces get one per workspace root, not per directory (A1/A3 ●, A2 ◐, A5 ◐); it cannot name other tools (A4 ○). Matching files are excluded from "the file listing Cline sees when starting a task", automatic context gathering and search results, but the docs state plainly that the file "is not a security or access-control boundary — ignored files can still be read via explicit @ mentions or shell commands" (B1 ◐). The hook "cancels the tool call before it runs — the file is never accessed", and the script reads .clineignore afresh on every call (B4 ◐). Its shell guard "is a conservative token check, not a full shell parser … a sufficiently creative command could still slip through" (B2 ◐); it "also blocks attempts to modify .clineignore itself so the agent cannot un-ignore files", though the hook file itself is not on its list (C3 ◐); "Paths are canonicalized lexically, but symlinks are not resolved" (D2 ◐); and "In the CLI, hooks are disabled in --yolo mode", so a blanket mode lifts the restriction (C1 ○, D3 ○). Subagents run with "Cline's built-in tools for the current mode", and "Approval settings don't apply inside a subagent"; whether hooks run for a subagent's tool calls is not stated (D4 ?). Error handling for a malformed or unreadable .clineignore and whether the policy reaches model context are undocumented (?).

Read, shell and write gating, timing, self-protection, canonicalization, and delegation of restrictions are undocumented (B1–B4, C3, D2, D4 ?).

JetBrains AI Assistant / Junie AI Assistant 263.6800.10, Junie 262.2144.120

.aiignore uses "the same syntax as a .gitignore file" (A1/A3 ●), and AI Assistant also honors .cursorignore, .codeiumignore, or .aiexclude "as long as they are located in the root folder of the project" (A5 ◐); .noai "in the root directory of the project" is a whole-project kill switch (docs). Junie reads .aiignore "in the project root directory" (Junie docs), not per directory (A2 ◐). The file names no tool and binds only Junie: AI Assistant's agents page lists .aiignore as "Respected" for Junie and "Not respected" for Claude Agent, Codex, and GitHub Copilot, and "files listed in .aiignore can be processed by Claude Agent" (Claude Agent) (A4 ○). Enforcement is vendor-admitted best-effort: "ignored files may still be processed due to unforeseen issues" (docs), and "Only the contents of files listed in .aiignore are protected" (Junie docs); file names and paths stay visible (support KB) (B1/D1 ◐). Edits to ignored files are approval-gated rather than hard-blocked: Junie "will ask for explicit approval before viewing or editing" them (Junie docs) (B3 ◐). The Junie docs name two exceptions where Junie "might still have access to the files listed in .aiignore": "If Brave Mode is turned on", and "When executing a command that is added to the Action Allowlist". So a remembered allowlist entry and a bypass mode both lift the restriction: "if a command is allowlisted, Junie will not ask for confirmation, even if that command accesses files and folders listed in .aiignore" (support KB) (C1 ○). Other shell access stays approval-gated (B2 ◐), and Brave Mode lets Junie "execute all potentially sensitive actions without user approval" (D3 ○). These statements are from the IDE plugin; the Junie CLI docs do not mention .aiignore. Timing, fail direction, self-protection, policy-as-data, canonicalization, and delegation are undocumented (B4, C2, C3, C4, D2, D4 ?).

OpenAI Codex CLI 0.162.0

The long-standing read-restriction gap has begun closing: beta permission profiles ("Beta. Permission profiles are under active development and may change.") add per-path filesystem rules — a deny entry "Denies both reads and writes under the path", and glob deny entries are supported — configurable in project .codex/config.toml files: "Codex walks from the project root to your current working directory and loads every .codex/config.toml it finds", "the closest file to your working directory wins", and "Codex loads project-scoped config files only when the project is trusted" (advanced config). User-authorable per-path rules exist, in beta (A1/A3 ●); the files travel with the repo, but which ones apply depends on where the session starts, not on the path being accessed (A2 ◐). The .codexignore request #1397 was closed as a duplicate; its successor #2847 was closed as completed on 2026-06-29, a maintainer citing "a new feature in beta that implements this functionality". The format is a Codex-specific TOML profile (A5 ○), and a profile names no agent (A4 ○). A read grant means "Commands cannot create, modify, rename, or delete files there" (B3 ●). The profile semantics lean fail-closed: "When two entries target the same path, deny takes precedence over write, and write takes precedence over read", though "A more specific path can also reopen a narrower subtree inside a broader deny"; "Missing or empty filesystem tables keep filesystem access restricted and emit a startup warning", and "If the selected policy cannot be enforced by the platform sandbox, Codex refuses to run the command instead of silently running it unsandboxed" — but "If sandbox_mode appears in any loaded config file … Codex uses those older sandbox settings instead of default_permissions" (C2 ◐). Extending :workspace "keeps the workspace root's .codex directory read-only unless you explicitly override it" (C3 ◐). The deny list is enforced in sandbox code, but the harness also writes the denied paths and globs into model context as a developer message — "The active permission profile denies reading these paths/globs" (source) — so the names of denied paths reach the model (C4 ◐, B1 ◐). The enforcement substrate is an OS sandbox (macOS Seatbelt, Linux bubblewrap): "The sandbox applies to spawned commands, not just to built-in file operations", and commands like git or test runners "inherit the same sandbox boundaries" (sandboxing) (B2/B3 ●, D1 ●); rust-v0.162.0 fixed a crack in that substrate, where a user ripgrep config could leave "files matching deny globs unmasked" (#51527). "Subagents inherit your current sandbox policy" (subagents), but "Connectors, MCP servers, browser or computer-use surfaces, Codex cloud environment settings, and approved escalations use their own controls" (permissions) (D4 ◐). Whether an edited profile reaches a running session without a restart is undocumented; on Linux, WSL and Windows, deny-read globs are expanded when "Codex snapshots matches before sandbox startup" (B4 ?). On Linux, an approved command will "Preserve literal deny paths alongside resolved targets so Linux can reject denials that cross writable symlinks" (#48155) (D2 ◐). Approved commands "retain explicit filesystem denials" (rust-v0.159.0), and "Approved filesystem escalation can now grant broader write access while preserving denied reads" (rust-v0.161.0), yet :danger-full-access "removes local sandbox restrictions" (permissions) (C1 ◐). That blanket mode is the only lift short of editing the rule: there is no one-invocation override, and the model is told "Do not request escalation or additional permissions to read them" (D3 ○).

Pi 1.1.0

Ships no file-access rules: an issue on its tracker lists the only mechanisms as the coarse --tools flag, custom TypeScript hooks, and interactive confirmation (#4459, which proposed native allow/deny policy files and was auto-closed during a refactor: "Issues closed during this period will not be reviewed") (A1–B4 ○, C1–C4 and D1–D3 —). The security doc places safety outside the harness — "Safety comes from limiting the files, credentials, processes, and network services Pi can access and affect" — and spells out the consequence: the working folder "does not prevent commands from accessing other paths available to the Pi process", project trust "does not limit what tool calls can access or affect", and child processes "run with those same permissions" (D4 ○); it also counts "lack of a built-in sandbox" as expected behavior. What Pi does have is a deterministic enforcement point: the tool_call hook can block operations in host-side code before execution. The shipped permission-gate example blocks three pattern-matched bash commands (rm -rf, sudo, chmod/chown 777) when no UI is present, and a sibling protected-paths example blocks write/edit calls to a hard-coded list (.env, .git/, node_modules/). A policy layer could attach there, but these are opt-in examples: with no restriction shipped, there is nothing for the harness to enforce yet (D1 —).

Windsurf / Devin Devin Desktop 3.10.48, CLI 3000.11.3

.devinignore (with legacy .windsurfignore / .codeiumignore "still read and enforced alongside .devinignore"), gitignore syntax, one file at "the root of your repository": paths matched "are excluded from indexing and cannot be viewed, edited, or created by Devin" (docs) (A1/A3 ●, A2 ◐, A5 ◐, B3 ●); whether the names of ignored paths stay out of listings and context is not stated (B1 ◐). Since v3.9.19, "Cascade has been removed" and "Devin Local is now the only agent available in Devin Desktop" (changelog); Devin Local shares Devin CLI's permission rules, where "A deny rule always wins", and v3.7.16 has rules "from different levels (enterprise, mode, user, project, subagent) now compose predictably — an explicit deny: always wins". But the precedence table still ranks "Session-level grants (interactive approvals)" above project and user config, and only "Organization-level deny and ask rules cannot be overridden by project or user config" (C1 ◐). The same holds for Bypass mode, where "all tool calls are auto-approved without prompting": only organization rules are guaranteed against it (D3 ◐). Smart mode's model judgment "only applies where no rule already decides the call, so a deny rule blocks the action" (D1 ●); the .devinignore docs do not name where that file is enforced. An opt-in OS sandbox hides Read(...)-denied paths "from sandboxed commands entirely", "hidden for the whole session" (B2 ◐), and errs restrictive in places — non-Exec rules in sandbox.excluded are "ignored with a warning", and if sandbox resolution fails, the CLI "will refuse to start rather than running unsandboxed" — but not everywhere: on Linux, "unsupported glob rules are ignored and logged" (CLI v3000.4.16) (C2 ◐). The edit, write, apply_patch, and notebook_edit tools "now refuse to write through a symlink" (Desktop v3.6.27, CLI v3000.3.27), with reads unstated (D2 ◐), and background subagents "inherit any tool permissions you have already granted during the current session"; "Any tool that has not been pre-approved is automatically denied" (D4 ◐). Unstated: whether edits to rule files take effect mid-session (B4 ?), whether the agent is barred from editing .devinignore or .devin/config.json (C3 ?), and whether ignore patterns or rules enter model context (C4 ?).

Zed 1.23.2

private_files and read_only_files glob settings, project-resident (all settings); project settings files can also sit in subdirectories — "You can also add settings files in subdirectories for more granular control" (configuring Zed) — and the agent's file tools look the settings up for the path being accessed (source) (A1/A2/A3 ●). Tool permissions add path-matched always_deny rules for edit_file, write_file, delete_path, move_path and create_directory (B3 ●). Content of private files is gated, and list_directory and grep skip private entries, but find_path returns matching worktree entries without a private_files check (source), so names can still reach the model (B1 ◐). The terminal tool is governed by command-pattern rules, not path rules, and under the OS sandbox "Terminal commands can read most of the filesystem" (B2 ○). Fail direction is split: an invalid tool_permissions regex blocks the tool — "If any patterns failed to compile, block the tool call entirely" (source) — while v1.22.0 only stopped one invalid file pattern from discarding the valid exclusion/read-only/private rules beside it: the invalid entry itself is still dropped, only logged, and "If the combined set cannot be built, reports the error and matches nothing" (#64525, source) (C2 ◐). always_deny is "highest priority, cannot be overridden", and global auto-approve leaves "always_deny, always_confirm, built-in security rules, and paths inside Zed settings directories" still prompting or blocking (C1 ●). Agent edits inside .zed/, where project private_files live, always prompt (source), but sandboxed "Terminal commands can write inside open project directories, except for protected Git metadata" (C3 ◐). The sandbox's own restrictions lift through remembered grants, for "the rest of the current thread" or "always", up to allow_unsandboxed (D3 ◐). Subagents get "the same tools as the parent agent" (tools), so the file-tool checks carry, but processes spawned from the terminal are not bound by private_files, and the sandbox "does not sandbox … External Agents" (D4 ◐). Enforcement is deterministic editor code, confirmed by the project's own advisory for CVE-2026-27967: agent file tools checked private_files on logical paths, so symlinks escaped; patched in 0.225.9. Today, symlinks resolving outside the project trigger an always-prompt, while the private check still runs on the project-relative path (D1 ●, D2 ◐). Not documented: whether a settings edit reaches a running agent before its next operation (B4 ?), and whether private-file patterns or names enter model context (C4 ?). Rules name no agent (A4 ○) and use Zed's own settings format (A5 ○).

Method

Scored from primary sources wherever possible: vendor documentation, public source code, the project's own issue tracker, and security advisories. A ? means no authoritative statement was found either way — inference is not scoring. A ◐ with a fixed CVE means the mechanism exists and its failure mode is documented history, not that the current version is broken. OpenCode and OpenHands are not yet scored: a row here requires the full source pass. Re-scored as harnesses ship; dated changes land in the scoring history below.

Landscape shifts

Directional changes in agent harnesses, and in the operating systems they run on: not every feature, only the moves that change where file-access policy lives, who decides, or which way it fails.

Contributing

To add an issue, open a pull request to the harness.fail repository with a source, the affected harness, the date it was first disclosed, and one or two factual sentences on what failed. If it was fixed, name the version that fixed it.

Primary sources are preferred: an advisory, a CVE record, a vendor announcement, or the researcher's own write-up. Press coverage is fine when no first-hand account is public.

To dispute a matrix score, or to correct anything else on the page, open a pull request.
